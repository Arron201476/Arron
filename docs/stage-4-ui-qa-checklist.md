# 阶段 4 UI / UE 全局审计标准

状态：v2.4 审计标准，当前执行结果单独记录  
版本：v2.4  
日期：2026-07-31

## 1. 审计目标

本审计用于判断 Figma 是否达到可交付前端实现的 UI / UE 质量，不用于证明代码、接口或模型已经完成。

以下结果不能单独证明视觉通过：

- 节点没有越界；
- 使用了组件实例；
- 原型跳转有效；
- 全页缩略图看起来完整；
- 某一个视口没有裁切；
- 结构扫描结果为 0。
- 用户没有发现明显流程问题；
- 页面没有明显视觉 Bug。

视觉通过必须同时具备全页观察、局部放大、几何测量、状态组合和修复后复核证据。

“没有坏掉”只代表基础正确性，不代表界面已经达到专业视觉质量。流程验收、可用性验收和视觉成熟度验收必须分别给出结论，任何一项不能替代另一项。

### 1.1 三层审计结论

| 层级 | 核心问题 | 典型证据 |
|---|---|---|
| 流程与产品逻辑 | 用户能否理解并完成任务 | 状态流、操作位置、异常恢复、审批路径 |
| 几何与可用性 | 页面是否稳定、可读、可操作 | 裁切、对齐、间距、响应式、长内容 |
| 视觉成熟度 | 是否达到可直接实现的专业产品质感 | 字体体系、密度节奏、组件精度、品牌识别、标杆差距 |

前两层通过而第三层未通过时，只能称为“流程完整的高保真线框稿”，不得称为视觉定稿。

### 1.2 独立判断要求

- 审计者必须先独立给出判断，再与产品负责人反馈对照。
- 产品负责人确认流程大致正确，不得被推断为视觉方向已确认。
- 产品负责人没有指出问题，不等于不存在视觉质量问题。
- 用户提出问题后不能只顺着问题补理由，必须说明此前为什么漏检、影响范围和新的防漏机制。
- 当现有设计明显停留在默认控件、临时拼装或通用后台质感时，即使没有裁切和对齐错误，也必须判定视觉成熟度未通过。

### 1.3 参考产品使用原则

- Oii、Flova 是当前参考样本，不是设计铁律或唯一答案。
- 参考产品用于拆解可迁移原则，例如信息层级、Agent 过程可见性、工作区关系、密度和反馈方式。
- 不直接照搬其布局、配色、组件外观、动效或业务假设。
- 参考结论必须结合本项目的内部用户、长文本生产、剧本编辑和多 Skill 工作流重新判断。
- 可以补充其他成熟的 Agent、编辑器和内容生产产品作为对照，避免被两个样本锁定。
- 每项借鉴都要记录“适用原因、不适用部分和本项目转译方式”。

## 2. 适用范围与职责边界

本文件只定义稳定审计规则，不保存会随设计修改而变化的 Frame ID、逐图结果和当前问题状态。

- 当前 Figma 真源、Frame ID、截图版本和审计批次记录在 `docs/stage-4-ui-evidence-manifest.md`；
- 当前发现、逐图结论和关闭状态记录在 `docs/stage-4-visual-audit-results.md`；
- 视觉方向、Tokens、组件语言和禁止项记录在 `design/stage-4/visual-baseline/`；
- Draft、Old、Archive 和重复响应式副本不得进入当前验收清单；
- Figma 只能证明设计意图和静态/原型状态，真实键盘、屏幕阅读器、浏览器兼容、性能和代码还原度由阶段 5 验证。

## 3. 审计顺序

必须严格按以下顺序执行：

1. 清理历史图并确认当前真源；
2. 审计 Foundations 和组件源；
3. 修复组件源；
4. 审计所有组件实例；
5. 审计标准业务页面；
6. 审计响应式和压力页面；
7. 审计原型交互；
8. 修复问题；
9. 对全部受影响页面复截图；
10. 形成产品负责人验收候选。

组件源没有通过时，不得继续宣布状态页面通过。

## 4. 每张图的强制证据

每张当前真源必须保留以下检查结果：

| 证据 | 要求 |
|---|---|
| 全页截图 | 以目标视口完整截图，检查整体层级、密度和视觉重心 |
| 关键区域局部截图 | 按 100% 比例检查 Header、工作区工具栏、Agent 事件卡和 Composer |
| 几何测量 | 记录关键容器宽高、内外边距、间距、贴边和对齐关系 |
| 状态检查 | 检查当前页面的 default / running / approval / error 等业务状态是否自洽 |
| 长内容检查 | 使用最长中文、长文件名、多 Chip、长按钮和长正文 |
| 视觉成熟度对比 | 与多个成熟产品或专业组件系统进行同区域对照，记录差距而不是只记录相似点 |
| 视觉方向证据 | 记录选定方向、被否决方向、Tokens、字体、密度和组件原则 |
| 修复后截图 | 任何问题修复后必须重新截取全页和受影响局部 |
| 证据身份 | 记录审计批次、标准版本、Figma 版本时间、Frame ID、截图文件和受影响组件 |
| 审计结论 | Pass / Fail / Blocked，不能使用“看起来没问题” |

没有局部截图、几何测量和视觉成熟度证据的页面，一律不能标记 Pass。

## 5. 全页视觉检查

### 5.1 信息层级

- 第一眼能区分全局导航、作品上下文、Artifact 工作区和 General Agent。
- 中间 Artifact 是主要阅读区域，右侧 Agent 不抢夺正文视觉重心。
- 页面标题、步骤状态、版本和主要动作有明确优先级。
- 不使用无意义卡片、边框、底色或装饰制造层级。

### 5.2 密度与留白

- 留白用于分组和阅读，不出现无法解释的空带。
- 页面上下、左右视觉重量平衡。
- 紧凑工具区不使用过大的间距；正文阅读区不被压缩。
- 空状态不能像未加载完成，密集状态不能像表格堆叠。

### 5.3 三栏关系

- 左、中、右三栏边界明确。
- 三栏在目标视口内不得横向滚动。
- 中间正文宽度满足阅读要求，宽屏不无限拉长。
- Agent Composer 固定在右栏底部，并与上方时间线形成连续结构。

### 5.4 视觉成熟度

- 界面不能只是默认表单控件、默认后台组件和灰色边框的组合。
- 字体大小、字重、行高和段落宽度必须形成稳定层级，而不是仅靠字号差区分。
- 紧凑工具区、长文阅读区、Agent 消息区应有不同但一致的密度节奏。
- Button、Input、Menu、Dialog、Tabs、Chip 和状态组件必须具有统一的光学细节和交互反馈。
- 色彩既要克制，也要有清晰的功能分工和产品识别，不能只靠单一强调色覆盖所有状态。
- 圆角、边框、阴影、分隔和背景层级必须有明确规则，不能保留组件库默认值或逐页临时决定。
- 第一眼应能判断这是面向长时间内容生产的专业工作台，而不是通用后台模板。

### 5.5 标杆差距检查

- 至少选择 3 个具有不同优势的成熟参考，不让单一产品定义答案。
- 对 Header、工作区、Agent 时间线、Composer、编辑器和 Dialog 做同区域并排比较。
- 只提炼原则，不以“做得像 Oii / Flova”为通过标准。
- 必须回答：本项目比参考产品更适合长剧本生产的地方是什么。
- 如果当前稿只能证明流程正确，不能证明专业质感，结论必须是 Fail 或 Blocked。

### 5.6 视觉方向契约

- 开始组件或页面视觉定稿前，必须只有一个当前有效的视觉方向契约。
- 契约必须明确产品气质、色彩角色、字体、密度、表面层级、组件语言、动效态度和反例。
- 每个参考必须记录 Keep、Change 和 Do not copy，不能只保存截图或产品名称。
- “专业、简洁、高级”等形容词不能单独构成约束，必须转译为可观察的排版、比例、材质和状态规则。
- 产品负责人确认流程不代表确认视觉方向；视觉方向必须单独留痕。
- 视觉方向变化后，旧截图和旧审计结论自动失效，必须生成新批次。

## 6. 关键区域局部几何检查

### 6.1 Header

- Logo、面包屑、状态、候选稿、最终稿和全局动作垂直居中。
- 左右操作区不贴边、不漂浮、不产生无意义空白。
- 文案变长时不能挤压状态或图标。

### 6.2 Artifact 工具栏

- 标题、版本、保存状态和 Edit 按钮处于同一视觉基线。
- 工具栏高度与按钮高度匹配。
- 不在工具栏中重复业务确认或 Agent 修改入口。

### 6.3 Agent 时间线和事件卡

- 时间线、普通文本、进度、审批、失败和结果卡之间间距一致。
- 卡片必须属于消息流，不能漂浮或脱离上下文。
- 卡片按钮贴合卡片底部操作区，不出现大块无意义空白。
- 长按钮、长说明和连续卡片不得裁切或挤压。

### 6.4 Composer

- Composer 必须贴合 Agent 面板底部，不留无法解释的外部空带。
- 输入框高度必须满足多行输入，不得显得窄、扁或拥挤。
- Prompt 在上，工具栏在下，中间使用弹性空间；工具栏必须锚定输入框底部。
- 工具栏与输入框边缘保持统一、可解释的内边距。
- `+`、Skill 和发送按钮在同一水平基线，点击区域高度一致。
- 发送按钮不能被裁切或漂浮；长 Skill Chip 必须自适应或截断。
- Context Chip 与输入框的距离、左右边界和换行策略必须明确。
- 348 / 392 / 420 三种右栏宽度都要单独检查组件源和页面实例。

### 6.5 Menu、Dialog 和浮层

- 三点按钮先打开锚定菜单，菜单贴合触发点。
- Dialog 位于页面视觉中心，遮罩强度合理。
- 标题、说明、影响信息和按钮区间距清晰。
- 危险操作与取消操作对齐，按钮文字上下左右居中。
- 浮层不得遮挡用户判断当前对象所需的关键信息。

### 6.6 列表、目录和任务行

- 行高一致，状态与标题不重叠。
- 长标题截断后保留可识别信息。
- 当前、待处理、完成和失败状态有一致语义。
- 12 集任务和 50 集目录必须验证滚动、固定行高和底部边界。

## 7. 组件源检查

每个组件源必须满足：

1. 使用 Auto Layout 表达真实结构，不靠手动坐标碰巧对齐；
2. 固定宽高有业务依据，FILL / HUG 使用正确；
3. 内边距、元素间距和圆角来自统一 Token；
4. Button 文案和 IconButton 图标光学居中；
5. default、hover、pressed、focus-visible、disabled 状态完整；
6. 长中文、长文件名和多 Chip 不破坏组件；
7. 组件源通过后，仍需检查所有业务实例；
8. 实例局部覆盖不得破坏组件的响应式约束。

### 7.1 Foundations 门禁

组件审计前必须先通过以下基础系统：

- 字体：中文字体回退、字号、字重、行高、段落宽度、数字和中英文混排均有固定规则；
- 图标：使用同一图标体系，描边、光学尺寸、基线和填充/线性风格一致，禁止用文字字符代替图标；
- 色彩：使用语义色 Token，正文、弱文本、边界、焦点、状态和破坏性操作职责明确；
- 几何：间距、控件高度、圆角、边框和层级来自统一 Token，不允许页面级随意新增近似值；
- 表面：Canvas、Rail、Paper、浮层和状态模块的边界与明度关系明确；
- 变更：新增 Token 必须说明用途，禁止为了修复单个页面绕过现有系统。

### 7.2 组件完成度门禁

组件“功能正确、文字居中、没有越界”不代表视觉完成。每个核心组件还必须从以下维度独立审计：

| 维度 | 检查内容 |
|---|---|
| 轮廓与比例 | 高度、宽度、圆角、点击区和光学重心是否有明确体系 |
| 内容构成 | 文字、图标、快捷键、状态标记和间距是否形成清楚层级 |
| 表面处理 | 填充、边框、分隔、阴影或高光是否有目的，是否适配所在表面 |
| 交互反馈 | hover、pressed、focus-visible、loading、disabled 是否可感知且属于同一语言 |
| 语义关系 | Primary、Secondary、Destructive、Approval 等是否体现操作风险和上下文 |
| 家族一致性 | Button、Input、Select、Chip、Card、Composer 是否像同一产品的组件 |

“克制”和“粗糙”必须区分：

- 克制可以没有阴影、渐变或图标，但比例、字体、表面和状态必须经过设计；
- 粗糙通常表现为默认圆角矩形、纯色换皮、默认字重和任意内边距；
- 如果组件的主要设计依据只有“换一个品牌色”，应判定未通过；
- 不强制所有按钮增加图标、阴影或装饰，任何元素都必须有语义或交互作用；
- 采用专业组件库只能解决行为和可访问性底座，未经本项目视觉系统转译的默认样式不能直接视为完成。

Button 必须额外检查：

- 文案是否准确表达动作结果，例如“确认并继续”是否比“确认继续”更清楚；
- 文字按钮和图标文字按钮是否有明确使用边界；
- Primary 不得只靠一块突兀的深色填充获得优先级；
- hover、pressed、focus-visible、loading 和 disabled 必须在 100% 比例下可区分；
- 放入 ApprovalCard、Dialog、Toolbar 和 Composer 后仍保持正确的视觉关系。

### 7.2.1 否决式视觉审计

组件不能因为状态齐全、变量绑定完整、没有越界或增加了图标、阴影、边框而从等级 2 自动提升为等级 3。候选必须先经过以下否决检查：

- 在 100% 比例和灰度观察下，Primary、Secondary、Destructive 的层级仍能被识别；
- 候选必须放入 ApprovalCard、删除确认 Dialog 和 Agent Composer 三个真实场景，不接受只在组件陈列区判断；
- 至少提出 2 套结构、比例或表面关系实质不同的方向；仅改变颜色、圆角、阴影强度或图标位置不算不同方向；
- 每套先记录支持证据和反对证据，再给出等级；不得先写“候选通过”再补理由；
- 如果第一眼仍可概括为“一个纯色圆角矩形加一行文字”，即使状态和 Token 完整，最高只能评为等级 2；
- loading 必须用稳定的进度符号替换原图标，禁止同时出现图标、圆点和省略号等重复反馈；
- focus-visible 必须属于产品表面体系，不能呈现为浏览器默认描边；
- 审计者必须主动寻找淘汰理由。产品负责人没有指出问题不能作为保留依据。

方向探索阶段最多向产品负责人提交两套通过内部否决检查的候选。没有候选通过时，应继续探索，不能为了推进阶段而降低等级标准。

### 7.3 组件质量试验板

在批量回刷页面前，必须先制作并验收一张组件质量试验板，至少包含：

- Primary、Secondary、Ghost、Destructive Button；
- IconButton 和 Tooltip；
- Input、Textarea、Select、Checkbox、Tabs、Chip；
- ApprovalCard、FailureCard、Agent Event；
- Composer；
- 默认、hover、pressed、focus-visible、loading、disabled、error 和长内容状态；
- 白色、浅色和强调色上下文中的真实组合。

试验板未通过时，不得用同一批组件继续组装或回刷业务页面。

### 7.4 组件判定尺度

每个核心组件按以下四级独立判定，不取平均分：

| 等级 | 定义 |
|---|---|
| 0 缺失 | 必要状态、结构或语义不存在 |
| 1 默认 | 可用，但明显是组件库默认样式、纯色换皮或临时拼装 |
| 2 成形 | 比例、排版和状态基本自洽，但仍缺少光学精度、上下文适配或家族一致性 |
| 3 定稿 | 在真实业务上下文和全部必要状态下均专业、稳定且可直接交付实现 |

阶段 4 通过要求所有核心组件达到 3；任一核心组件为 0 或 1 时计为 P1，不能被其他组件的高分抵消。

禁止：

- 在业务 Frame 中手画 Button、Chip、输入框或事件卡；
- 用文字字符伪装图标；
- 只检查组件源，不检查实例；
- 通过增加 `clipsContent` 隐藏错误；
- 用“没有越界”替代视觉判断。
- 把组件库默认样式直接当成产品视觉；
- 仅换颜色后宣称组件完成；
- 先批量回刷页面，再补组件精度。

## 8. 状态与产品逻辑检查

- 用户只聊天时不得误启动 Skill Run。
- 意图不明确时先追问。
- 已确认产物不得静默覆盖。
- 暂停、恢复和局部重试保留已完成版本。
- 审批按钮只位于 Agent 流内的 ApprovalCard。
- 缺集时阻止自动继续，直到补传或明确确认。
- 失败页保留当前产物，提供局部恢复动作。
- Agent 使用业务语言，不暴露内部模型、Prompt、Rule、Worker 或异常堆栈。
- 小说、非小说和视频参考创作最终都闭环到可编辑剧本。

### 8.1 文案与术语

- 用户侧统一使用已确认的产品术语，不混用 Skill、Capability、能力、Run、Step 和内部节点名。
- Button 使用结果导向文案，避免含义不完整的“确定”“继续”“处理”等孤立词。
- 空状态、加载、失败、暂停和恢复文案必须回答“发生了什么”和“用户下一步能做什么”。
- 错误信息不暴露内部堆栈，也不能只写“操作失败”而不给恢复路径。
- 同一动作在不同页面使用相同名称，危险操作明确说明影响范围。

状态逻辑通过不能抵消视觉几何问题，视觉通过也不能抵消状态逻辑问题。

## 9. 响应式与压力矩阵

| 维度 | 必测内容 |
|---|---|
| 1280 x 800 | 中间工作区最小宽度、Agent 348px Composer、长审批按钮 |
| 1440 x 900 | 标准三栏、392px Composer、所有主要状态 |
| 1920 x 1080 | 正文限宽、420px Composer、宽屏视觉重心 |
| 长中文 | 作品名、文件名、步骤名、按钮、Chip、说明 |
| 密集任务 | 12 集视频任务、连续 Agent 卡片 |
| 长目录 | 50 集、滚动、当前项、最后可见项 |
| 编辑内容 | 长剧本、长对白、长段落、多个选区 |

## 10. 可访问性和交互检查

- 所有 IconButton 在实现中必须有 Tooltip 和 `aria-label`。
- 键盘焦点顺序与视觉顺序一致。
- focus-visible 清楚但不过度抢眼。
- 状态不能只依赖颜色，必须有文字或形状辅助。
- 设计色彩以 WCAG 2.2 AA 对比度为目标，阶段 4 记录静态计算证据，阶段 5 用真实 DOM 复测。
- 点击区域不小于组件规范。
- Prototype 目标必须有效，但原型有效不代表视觉通过。
- 加载、生成、暂停、恢复和重试不得造成主要布局跳动或重复提交。
- 设计必须标明流式输出、局部更新、等待和按钮提交中的反馈方式。
- 200% 缩放、键盘可达性、屏幕阅读器播报和减少动效在阶段 5 验证，不从 Figma 截图推断通过。

## 11. 问题分级

| 等级 | 定义 | 门禁 |
|---|---|---|
| P0 阻断 | 主流程无法理解、关键操作缺失、内容严重裁切、状态错误 | 必须立即修复 |
| P1 明显 | 对齐、贴边、留白、输入尺寸、层级、响应式、组件质感或整体视觉语言明显不专业 | 阶段 4 不得通过 |
| P2 细节 | 文案、光学对齐、轻微间距或样式一致性问题 | 定稿前修复 |

每个问题必须记录：

- 审计批次和标准版本；
- 页面和 Frame ID；
- 组件或实例 ID；
- 问题等级；
- 复现截图；
- 预期规则；
- 修复位置；
- 修复后截图；
- 复核人和结论。

## 12. 结果与证据管理

- 逐图结论不得复制到本标准中，统一维护在 `docs/stage-4-visual-audit-results.md`。
- 当前 Frame、截图文件、哈希、Figma 修改时间和适用标准统一维护在 `docs/stage-4-ui-evidence-manifest.md`。
- 验收入口只展示当前批次；历史证据移入带日期的 Archive，不与当前候选并列。
- 组件源变化后，所有直接实例和受影响页面自动回到 Pending。
- 页面结构或视觉方向变化后，旧 Pass 不得沿用。
- 修复只重审受影响页面不足以关闭阶段门禁；提交产品负责人前必须再执行一次全量代表性回归。

## 13. 阶段通过门禁

阶段 4 只有同时满足以下条件才能进入产品负责人确认：

1. 当前证据清单中的全部必验 Frame 均为 Pass；
2. 所有 P0 / P1 已关闭；
3. P2 已关闭或有产品负责人明确接受记录；
4. 组件源和全部实例均已复核；
5. 三个目标视口和压力状态均通过；
6. 原型命名路径有效；
7. 验收记录包含全页和局部证据；
8. 视觉成熟度对比完成，且不是只与 Oii、Flova 两个样本比较；
9. 组件质量试验板通过，核心组件不再停留在默认控件或纯色换皮状态；
10. 产品负责人分别确认流程方向和视觉方向，不能合并为一次模糊确认；
11. 文档、Figma 和机读状态一致。

当前状态不在本标准中维护，见 `docs/stage-4-visual-audit-results.md`。
