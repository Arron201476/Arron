# 内容生产 Agent 第一版产品定义

状态：阶段 1 已确认基线  
版本：v1.0  
日期：2026-07-24

## 1. 文档目的

本文档用于固化内容生产 Agent 第一版已经对齐的产品方向、用户流程、能力边界和验收标准。

本文档只定义第一版“做什么”和“用户如何使用”，不提前确定数据库表、API、Eino Graph、前端组件和模型调用实现。这些内容进入阶段 2 后设计。

### 1.1 决策状态

文档中的产品条目使用以下状态：

- **已确认**：已经在阶段 1 讨论中明确，不应在阶段 2 被实现细节反向改变；
- **建议默认**：符合现有项目经验和第一版范围，但仍需要产品负责人确认；
- **待确认**：会改变第一版范围、交互或数据策略，未得到明确答案前不能视为最终需求；
- **阶段 2 定义**：产品行为已明确，但对象、Schema、API 或实现方式留到架构阶段。

## 2. 产品定位

### 2.1 一句话目标

为需要通过多种来源获得漫剧生产前剧本的用户，提供一个交互轻量、过程可控、产物可编辑的通用内容生产 Agent。

第一版最终生产结果统一为：

```text
可编辑、可确认、可继续修改的分集剧本
```

### 2.2 目标用户

- 公司内部使用内容生产平台的业务用户；
- 需要从小说生成漫剧剧本的用户；
- 需要从故事大纲、集纲、人物设定等非小说材料生成剧本的用户；
- 需要分析热门漫剧视频并参考其创作新剧本的用户；
- 对 Agent 产品不熟悉，主要使用过聊天模型的内容生产用户。

### 2.3 第一版设计原则

- 对话优先，减少强制填写表单；
- Agent 主动识别意图，用户也可以显式选择 Skill；
- 生成过程中的主要产物必须经过用户确认；
- 所有用户可见产物支持编辑、要求 AI 修改、重新生成和版本记录；
- 通用能力只在 Agent Shell 建设一次，不在每个 Skill 中重复实现；
- Skill 负责领域工作流，Rules 负责具体专业规则；
- 第一版先保证三条主链路完整、稳定，不追求覆盖所有可能的 Skills。

### 2.4 第一版完整用户旅程

```text
进入作品入口
→ 打开已有作品，或通过对话/上传材料创建新作品
→ Agent 理解需求并识别 Skill
→ 信息不足时追问最少必要信息
→ 用户确认生成配置
→ 有状态生产 Skill 经配置确认后创建 Run 并开始执行
→ 每个主要业务步骤生成可编辑产物
→ 用户查看、编辑、要求 AI 修改或重新生成
→ 用户确认后进入下一步骤
→ 生成完整分集剧本
→ 用户确认、继续修改或导出
→ 作品保留，可随时恢复继续
```

第一版不是“一次聊天返回一段文本”，而是围绕一部作品持续保存材料、任务、产物、确认和最终剧本。

## 3. 行业对齐与产品选择

当前主流生产型 Agent 通常采用以下分层：

```text
长期工作容器
→ Agent 对话与任务
→ Skills / Workflows
→ Tools / Models / MCP
→ 持久化产物与运行状态
```

代码 Agent 通常由代码仓库或工作区天然承担长期工作容器。内容生产没有天然代码仓库，因此本产品使用“作品”作为长期工作容器。

本项目采用：

```text
作品
→ 作品工作台
→ 同一个通用 Agent
→ 按意图调用不同 Skills
→ 生成和管理作品产物
```

这与主流 Agent 的“工作区 + 对话 + 可调用能力”结构一致，但界面和产物针对漫剧剧本生产定制。

当前产品判断参考：

- [ChatGPT Projects](https://help.openai.com/en/articles/10169521-using-projects-in-chatgpt)：项目聚合聊天、文件、指令和长期上下文；
- [Claude Projects](https://support.anthropic.com/en/articles/9517075-what-are-projects)：项目作为独立工作区，包含聊天历史和知识库；
- [Cursor Rules](https://docs.cursor.com/context/rules)：项目规则按代码库生效，代码仓库隐式承担工作容器；
- [OpenAI Build skills](https://learn.chatgpt.com/docs/build-skills.md)：Skill 由指令、资源和可选脚本组成，并按需加载；
- [OpenAI MCP](https://learn.chatgpt.com/docs/extend/mcp)：外部工具和上下文能力与 Skill 工作流分层组合。

## 4. 核心概念与命名

### 4.1 Agent Shell

通用 Agent 本体。即使不挂载任何领域 Skill，也能完成对话、理解意图、处理通用输入、维护当前作品上下文，并说明当前是否具备完成任务的能力。

### 4.2 Skill

用户可显式选择，或由 Agent 根据意图自动选择的一项完整业务能力。

第一版 Skills：

1. 小说转剧本；
2. 非小说文本转剧本；
3. 视频参考创作。

### 4.3 Capability

后端架构中对 Skill 对应领域模块的命名。产品界面统一使用“Skill”，代码和架构可以使用 `capability`。

### 4.4 Rules

Skill 在执行具体步骤时按需读取的专业规则，例如对白规则、剧本格式规则、视频高还原剧本生成规则。

Rules 不作为用户可选择的完整能力，不与 Skill 混用命名。

### 4.5 Tool / Model / MCP

真正执行某项操作的底层能力，包括模型调用、视频理解、文件解析、公司内容库和未来外部服务。

Skill 规定何时、以什么输入、按照什么流程调用它们。

### 4.6 Runtime

保存不能依赖模型记忆的业务事实，包括作品、Run、步骤状态、Artifact、版本、审批、暂停、恢复和失败重试。

## 5. 信息架构

### 5.1 作品入口页

作品入口页承担长期工作容器的选择和创建，不是营销首页，也不是复杂项目管理后台。

第一版包含：

- 最近作品列表；
- 搜索和打开已有作品；
- 新建作品；
- 作品当前状态；
- 直接输入需求或上传材料并自动创建作品。

作品状态示例：

```text
等待上传
视频解析中
等待确认
剧本生成中
剧本已完成
生成失败
```

### 5.2 作品工作台

进入一部作品后显示主操作页面：

```text
左侧：当前作品的流程和产物目录
中间：当前产物或剧本编辑器
右侧：统一 Agent 对话
顶部：作品名称、当前 Skill、运行状态
```

第一版只提供桌面网页端。工作台以桌面浏览器完整创作为目标，不建设原生桌面端、移动端应用，也不把手机浏览器适配纳入第一版设计和验收范围。

### 5.3 作品与对话

第一版采用：

```text
一部作品
= 一个工作台
= 一个连续主对话
= 多个 Skill 运行记录
= 多个可编辑产物
= 一个最终确认的分集剧本
```

底层仍分别保存 `project_id` 和 `conversation_id`，不把两者合并为同一对象。

同一作品在最终剧本确认前，可以由不同 Skill 和不同 Run 产生多个候选剧本版本。所有候选版本、来源 Skill、生成配置和上游产物关系都需要保存。作品只能有一个当前最终剧本；确认某个候选版本为最终剧本时，其他候选版本继续保留为历史，不被删除或覆盖。

用户可以从历史候选剧本中重新选择一个版本设为当前最终稿。首次设为最终稿和后续改选都必须再次确认；改选不会删除之前的最终版本和其他候选版本。

### 5.4 创建和切换作品

- 用户没有当前作品时启动创作，系统可自动创建作品；
- 用户也可以通过“新建作品”主动创建；
- 用户在当前作品中明确要求创作另一部作品时，创建并切换到新作品；
- 用户上传明显无关材料且意图不明确时，Agent 询问加入当前作品还是创建新作品；
- 作品之间的对话、文件、任务和产物默认隔离。

### 5.5 作品生命周期

第一版至少需要覆盖以下生命周期：

```text
创建
→ 添加材料
→ 运行 Skill
→ 等待确认 / 暂停 / 失败
→ 完成剧本
→ 后续修改
→ 再次打开并恢复
```

作品入口必须能恢复：

- 最近一次查看的产物；
- 当前 Run 和步骤状态；
- 当前有效审批；
- 已上传材料；
- 最新产物版本；
- 主对话记录。

第一版已确认提供：

- 新建作品；
- 打开作品；
- 重命名作品；
- 删除作品。

归档、回收站、恢复已删除作品和复制作品不作为第一版已确认操作。

### 5.6 Skill 入口与自动路由

第一版同时支持两种入口：

1. 用户显式选择或引用 Skill；
2. 用户直接描述需求，由 Agent 自动路由。

路由规则：

- 用户明确指定 Skill 时，优先遵循用户选择；
- 用户没有指定但意图清楚时，Agent 直接选择匹配 Skill；
- 小说与非小说来源判断不充分时必须追问；
- 单纯上传、闲聊、查看材料或讨论创意不自动启动 Run；
- 启动正式生成前必须补齐该 Skill 的必需输入和生成配置；
- 当前作品已有运行中任务时，不允许静默启动第二个冲突 Run。

工作台在输入框上方提供一个“Skill”按钮。点击后展开包含三个 Skills 的菜单；用户点击某个 Skill 后，将对应 Skill 名称作为可识别引用插入输入框。用户可以继续补充材料、目标和要求，发送消息后才进行意图判断或启动前置询问，插入 Skill 本身不立即创建 Run。

用户也可以不点击 Skill 按钮，直接用自然语言描述需求，由 Agent 自动路由。

第一版不支持把小说、非小说和视频材料任意融合成一条新链路。每个生成 Run 只选择一条主链：

- 小说材料进入小说转剧本主链；
- 非小说材料进入非小说文本转剧本主链；
- 视频参考创作按已确认流程完成解析、分析和 `adaptation_brief` 后，只接入非小说后续创作链。

同一作品可以保留多个 Skill 产生的候选剧本版本，但一个 Run 内不能混用多条未定义的主链。

## 6. 项目上下文策略

一个作品对应一个独立的逻辑上下文空间，但每次模型调用不读取作品内的全部内容。

逻辑上下文包括：

```text
作品摘要
对话记录
输入材料
已确认产物
当前任务和步骤状态
审批与版本信息
```

模型调用时按层级组装：

1. 主 Agent 读取作品摘要、当前任务状态和近期对话，用于意图判断；
2. Skill 读取当前业务流程需要的产物；
3. Worker 只读取执行当前步骤所需的最小材料；
4. 用户选中的文本或产物范围拥有最高定位优先级。

项目之间不读取彼此上下文。第一版不支持跨作品引用；用户需要把所需材料明确添加到当前作品，Agent 不自动读取其他作品的文件、对话或产物。

## 7. Agent Shell 第一版能力

### 7.1 必须具备

- 自然语言对话；
- 意图识别；
- 用户显式选择 Skill；
- 根据意图自动路由 Skill；
- 意图不确定时主动询问；
- 通用文本、图片、视频和文件输入；
- 当前作品上下文维护；
- Run 和步骤状态展示；
- 暂停、恢复和失败重试；
- Artifact 展示、编辑和版本记录；
- 用户确认后进入下一步骤；
- 通过对话要求 AI 修改产物；
- 用户选区定位和局部修改；
- 不具备所需 Skill 或 Tool 时说明缺少的能力。

### 7.2 不挂载领域 Skill 时

未挂载领域 Skill 时，Agent 仍可：

- 对话；
- 理解和解释用户提供的文字或图片；
- 判断用户意图；
- 使用已有通用工具；
- 告知用户当前不能执行哪项领域生产任务。

它不能仅凭聊天能力完成需要专门流程、工具或持久化产物的领域任务。

### 7.3 通用输入与 Skill 的边界

上传文字、图片、视频和文件属于 Agent Shell 的通用输入能力。

输入进入系统后由 Agent 判断：

- 只需要理解并回答；
- 加入当前作品作为材料；
- 调用某个 Skill；
- 意图不明确，需要询问用户。

能上传某种文件，不等于当前 Skill 自动具备处理该文件的全部业务能力。

### 7.4 输入材料管理

上传材料与启动 Skill 是两个动作：

- 上传成功只代表材料进入当前作品；
- 上传本身不创建 Run；
- Agent 根据当前消息决定是否读取材料；
- 用户应能查看材料名称、类型、大小、解析状态和所属作品；
- 多份材料同时存在时，Agent 必须明确本次使用哪些材料；
- 用户删除已被产物引用的材料时，系统必须提示影响，不能静默断开来源；
- 不支持或解析失败的文件应保留明确错误，不得显示为已成功读取。

第一版支持：

- 文本与文档：TXT、MD、DOCX、PDF；
- 图片：JPG、PNG、WebP；
- 视频：MP4、MOV。

具体单文件大小、单批数量和单作品数量上限，在接入正式接口并完成负载测试后配置化确定。

用户请求删除已被产物引用的源文件时，系统阻止直接删除，先说明受影响的产物和后续能力，并要求用户再次确认。用户确认删除后，已生成的派生产物不自动消失，但必须保留“源文件已删除”的来源状态。

**阶段 2 定义**：文件对象、解析结果、来源引用和删除影响的具体 Schema。

## 8. 通用运行与产物规则

### 8.1 审批原则

每个主要业务步骤完成后进入待确认状态。用户确认后才能进入下一主要步骤。

确认前用户可以：

- 直接编辑；
- 通过对话要求 AI 修改；
- 重新生成；
- 暂停流程。

产物修改后生成新版本，之前的确认自动失效，需要重新确认。

内部辅助产物和纯聚合视图不单独设置确认点。

### 8.2 批量步骤

批量任务采用“步骤级确认、子项级编辑”：

- 子项独立展示状态、保存、编辑、重生成和版本；
- 子项可并发或串行执行；
- 不要求用户逐项点击确认；
- 所有必需子项成功后，用户对整个步骤确认一次；
- 任一必需子项失败时，当前步骤不能确认。

全集剧本生成同样采用该规则：每个 `script_unit` 独立查看、编辑、重生成和保存版本；全部必需集数成功后，对整个剧本步骤统一确认一次，不要求逐集点击确认。

### 8.3 下游影响

用户修改已被下游消费的产物时，系统必须明确说明影响范围。

第一版至少支持：

- 保留现有下游产物；
- 重新生成受影响的下游产物。

不能静默使用不一致版本继续生成。

### 8.4 Run 控制语义

第一版必须区分以下操作：

| 操作 | 用户目的 | 产品行为 |
|---|---|---|
| 暂停 | 暂时停止，稍后继续 | 安全停在可恢复位置，保留当前进度 |
| 恢复 | 从暂停位置继续 | 读取同一批已确认输入和当前 cursor |
| 重试 | 修复失败任务 | 只从失败位置继续，不重复成功子任务 |
| 重新生成 | 主动换一版结果 | 基于用户指定的输入和要求创建新版本 |
| 取消 | 不再继续当前 Run | 停止后续任务，保留已产生的记录和产物 |
| 确认 | 接受当前主要产物 | 锁定当前版本作为下一步骤输入 |

模型自然语言回复不能自行完成确认、取消或重新生成。所有状态变化必须经过业务 Guard 和 Runtime。

运行互斥规则：

- 同一作品同一时间只允许一个会修改产物的活动 Run；
- 不同作品允许同时运行任务；
- 总并发上限由阶段 2 根据模型配额和服务负载配置；
- 第一版不提供隐藏任务队列，冲突操作应要求用户先暂停、取消或等待当前 Run。

### 8.5 运行中的对话和编辑

运行中不允许在当前作品继续发送聊天消息。输入框进入禁用状态，界面通过结构化状态直接展示当前步骤和进度，不依赖用户询问。

运行中用户仍可：

- 查看进度；
- 通过明确的运行控制请求暂停或取消；
- 切换到其他作品。

运行中默认不允许：

- 发送闲聊、修改要求或新的执行消息；
- 修改正在被读取的上游产物；
- 对同一作品启动另一个会写入产物的任务；
- 静默改变本次生成配置。

暂停并安全保存 cursor 后，用户可以编辑产物或补充要求，再决定恢复还是从受影响步骤重新生成。

### 8.6 输出验证

第一版必须进行确定性结构验证，包括：

- 输出能被解析；
- 必需字段存在；
- Artifact 类型与当前步骤匹配；
- 目标集数、集号唯一性和顺序正确；
- 来源引用指向真实文件或上游产物；
- 批量任务没有重复或遗漏成功子项。

第一版暂不承诺自动判断所有剧情内容是否正确，也不使用模型评分替代用户确认。语义质量由 Prompt/Rules、必要的确定性检查和用户审批共同保障。

### 8.7 完成与后续修改

Skill 的 Run 在最终剧本步骤确认后进入完成状态。完成不代表作品被关闭：

- 用户仍可查看和编辑最终剧本；
- 用户可以要求 AI 修改某一集、场景或选区；
- 用户可以基于已确认产物重新生成受影响内容；
- 历史完成 Run 和旧版本必须可追踪；
- 后续修改不能覆盖或伪装成原完成版本。

最终剧本确认后继续修改时，原已完成版本必须保留；手动修改、AI 修改或重新生成都会形成新版本和修订记录。新版本确认前不能静默替换当前最终稿。

新修改是创建修订 Run，还是复用现有 Run，由阶段 2 的运行协议确定。

### 8.8 生成配置

启动小说、非小说或视频改编的新剧本生成前，至少明确：

- 来源模式；
- 目标集数；
- 单集时长；
- 用户补充要求；
- 是否保留原有分集；
- 材料不足时的扩写/压缩策略。

规则：

- 用户已经在自然语言中明确的信息应自动提取，不重复询问；
- 缺少目标集数或单集时长时不能自行填默认值；
- 视频转参考剧本阶段使用原视频集数和时长，不要求填写新剧本配置；
- 配置一旦进入 Run，后续节点读取同一已确认版本；
- 用户中途改变配置时，应明确受影响范围并从正确步骤重算。

目标剧本字数、场次数量和内容密度可由单集时长推导，不要求新用户理解内部字符预算。

### 8.9 用户可见状态语言

产品必须区分：

- 待生成；
- 生成中；
- 已生成、待确认；
- 已确认；
- 修改后待重新确认；
- 已过期/受上游影响；
- 已暂停；
- 失败、可重试；
- 已完成。

“模型已经返回”只能表示已生成，不能显示为已确认。只有用户明确确认后，产物才能成为下游的已确认输入。

### 8.10 通知

第一版不建设独立通知系统，不发送短信、邮件、企业微信消息，也不要求额外的任务完成推送。用户通过作品入口和作品工作台查看当前状态、完成结果和待确认事项。

## 9. Skill 1：小说转剧本

### 9.1 目标

把用户上传或粘贴的小说原文转换为目标集数和时长的分集剧本。

### 9.2 输入

- 小说原文；
- 目标集数；
- 单集时长；
- 用户补充的创作要求。

如果原文存在可靠分集标识，可允许用户选择保留原有分集。否则必须确认目标集数和单集时长。

### 9.3 主流程

```text
上传或粘贴小说原文
→ 确认目标集数和单集时长
→ story_bible
→ 用户确认
→ episode_split
→ 用户确认
→ episode_cards
→ 用户确认
→ script_context（内部）
→ 逐集生成 script_unit
→ 用户确认剧本
→ 汇总 scripts（聚合视图）
```

### 9.4 主要产物

- `source_input`
- `story_bible`
- `episode_split`
- `episode_cards`
- `script_unit`
- `scripts`

### 9.5 各确认点解决的问题

| 产物 | 主要内容 | 用户确认重点 |
|---|---|---|
| `story_bible` | 核心故事、世界观、人物、关系、主线、关键设定和原文事实 | 是否正确理解原著，是否遗漏或误判关键事实 |
| `episode_split` | 原文范围到目标集数的拆分关系 | 每集边界、覆盖完整性、顺序和节奏是否合理 |
| `episode_cards` | 每集功能、开头承接、主冲突、关键事件、人物变化和尾钩 | 分集规划是否满足目标集数和单集时长 |
| `script_unit` | 单集场次、动作、对白、OS/VO、转场和来源引用 | 剧本是否可用，人物、剧情、格式和连续性是否正确 |

### 9.6 材料体量不足或配置不合理

在正式运行前或最早可判断的步骤，Agent 应识别：

- 原文体量明显不足以支撑目标集数；
- 原文体量过大，目标集数会导致过度压缩；
- 单集时长与目标内容密度明显冲突；
- 原文已有分集与用户目标集数不一致。

系统不能静默改变用户填写的集数和时长。应说明影响，并让用户选择调整配置、允许扩写/压缩，或继续按原配置执行。

小说链默认不新增原文之外的关键设定和主线。体量不足时必须先向用户说明缺口，并确认本次扩写策略；未经确认只能建议调整目标集数、单集时长或压缩范围，不能自行补出新的核心剧情。

## 10. Skill 2：非小说文本转剧本

### 10.1 目标

把故事大纲、集纲、人物设定、桥段、台词、世界观或其他非小说材料扩展和规划为分集剧本。

### 10.2 输入

- 非小说文本材料；
- 目标集数；
- 单集时长；
- 用户补充的创作要求。

缺少目标集数或单集时长时，不能启动正式生成。

### 10.3 主流程

```text
上传或粘贴非小说材料
→ 确认目标集数和单集时长
→ material_bank
→ 用户确认
→ story_seed
→ 用户确认
→ series_blueprint
→ 用户确认
→ episode_cards
→ 用户确认
→ script_context（内部）
→ 逐集生成 script_unit
→ 用户确认剧本
→ 汇总 scripts（聚合视图）
```

### 10.4 主要产物

- `source_input`
- `material_bank`
- `story_seed`
- `series_blueprint`
- `episode_cards`
- `script_unit`
- `scripts`

### 10.5 各确认点解决的问题

| 产物 | 主要内容 | 用户确认重点 |
|---|---|---|
| `material_bank` | 已有素材分类、明确事实、可用桥段、人物、设定、台词和缺口 | 材料是否被正确理解，哪些是已有内容，哪些仍缺失 |
| `story_seed` | 核心梗、主角目标、关系引擎、主要阻力、情绪驱动力和爽点链 | 扩写方向是否符合用户想法，新增设定是否可接受 |
| `series_blueprint` | 总集数、阶段结构、高潮安排、节奏和内容密度 | 整剧体量和结构是否能支撑目标集数、时长 |
| `episode_cards` | 每集功能、冲突、事件、人物变化、爽点和尾钩 | 分集内容是否连贯、重复、缺失或失衡 |
| `script_unit` | 单集场次、动作、对白、OS/VO、转场和来源引用 | 剧本可用性、连续性、人物声口和格式 |

### 10.6 材料补全原则

非小说材料天然可能不完整。系统必须区分：

- 用户明确提供的事实；
- 从材料合理整理出的结构；
- 为满足目标集数新增的创作内容；
- 尚未解决、需要用户回答的关键缺口。

新增内容不能伪装成用户原始材料。若关键设定缺失会显著改变故事方向，Agent 应先追问；非关键空白可在 `story_seed` 中提出并等待用户确认。

## 11. Skill 3：视频参考创作

### 11.1 目标

把热门漫剧视频解析为高还原参考剧本，分析其内容和创作方法，在用户确认改编方法后生成一部新的分集剧本。

### 11.2 输入

- 一部参考剧的一集或多集视频；
- 用户补充的改编要求和新元素；
- 新剧本目标集数；
- 新剧本单集时长。

视频上传是 Agent Shell 的通用输入能力。视频参考创作 Skill 负责解释视频在当前业务流程中的用途。

### 11.3 分批上传

- 用户可以分批上传同一部参考剧的视频；
- Agent 不根据等待时间猜测用户是否上传完成；
- 每批上传后，Agent 提示用户可以继续上传；
- 用户通过“传完了”“就这些”“开始处理”等自然语言结束上传；
- 可以提供“上传完成”按钮作为快捷方式，但不强制使用；
- 上传结束前不创建 Domain Run 或解析任务；
- 未收到用户完成意图前，不进入逐集解析、整剧合并和剧本分析。

### 11.4 视频排序和批量执行

- 默认一个视频对应一集；
- 按文件名中的自然集数排序；
- 单集视频独立显示解析状态；
- 允许失败单集重试；
- 单集结果支持保存、编辑和重新生成；
- 整个视频解析步骤统一确认一次，不要求逐集点击确认。

结束上传时，系统至少检查：

- 是否识别到集号；
- 集号是否重复；
- 集号是否存在明显缺口；
- 是否有上传或解析失败的视频；
- 当前展示顺序是否与用户预期一致。

无法从文件名可靠识别集号时，不直接猜测；系统提供按上传顺序暂排和人工调整集号/顺序的能力。存在缺集时允许用户显式确认“按不完整材料继续”，随后剧本分析必须标记材料完整度和缺失范围。

### 11.5 主流程

```text
用户分批上传视频
→ Agent 持续接收并解析单集
→ 用户明确表示上传完成
→ 检查顺序、明显缺集、重复和失败任务
→ 展示全部单集高还原剧本
→ 用户统一确认视频解析结果
→ 合并完整参考剧本（系统聚合）
→ 生成整剧剧本分析
→ 用户确认
→ Agent 主动提出 2-3 套改编方案
→ 用户选择、组合、自定义或要求 AI 修改
→ 生成整剧级 adaptation_brief
→ 用户编辑或要求 AI 修改
→ 用户明确确认 adaptation_brief
→ 进入非小说后续创作链路
→ story_seed
→ 用户确认
→ series_blueprint
→ 用户确认
→ episode_cards
→ 用户确认
→ 逐集生成新 script_unit
→ 用户确认剧本
→ 汇总新 scripts
```

### 11.6 视频解析阶段与改编阶段

视频转参考剧本时：

- 集数由上传的视频数量和文件名确定；
- 单集时长使用原视频实际时长；
- 不询问新剧本目标集数和单集时长。

开始改编生成新剧本前：

- 必须确认目标集数；
- 必须确认单集时长；
- 必须确认 `adaptation_brief`；
- 未确认改编方法时不能进入新剧本生成。

### 11.7 视频解析质量边界

第一版输出定位为“可编辑的高还原剧本初稿”，不是法律或字幕制作意义上的逐字转录稿：

- 综合画面、内嵌字幕、可辨认音频和关键屏幕文字；
- 优先保证核心剧情、人物关系、主要对白、反转和结尾钩子；
- 不确定内容必须标注，不能猜测补全；
- 对白、OS、VO、旁白、系统提示和关键屏幕文字需要区分；
- 保留来源视频和时间码引用；
- 不承诺逐帧 OCR、完整 ASR 或 100% 台词无遗漏。

第一版不额外接 OCR/ASR 做三模型交叉验证。若后续验收显示高还原质量不能满足用户使用，应重新评估专用字幕/OCR/ASR 管线，而不是在产品文案中声称已经逐字提取。

该质量边界已作为第一版基线接受。是否增加 OCR/ASR 必须依据真实视频样本的人工验收结果决定，不在第一版预先建设。

### 11.8 剧本分析

`script_analysis` 读取全部已确认的参考剧本，输出一份整剧级分析。根据已经提供的漫剧爆款诊断规则，第一版分析至少覆盖：

1. 基础信息、完整度、一句话概括、剧情简介和世界观；
2. 综合潜力、最大优势、最大短板和形态适配度；
3. 开头策略；
4. 核心梗与钩子系统；
5. 爽点、虐点和情绪释放路径；
6. 剧情驱动和情绪曲线；
7. 人物设定、人物关系和语言特征；
8. 逐集信息、关键冲突、结尾卡点和转化点；
9. 差异化和核心爆点；
10. 可复制的创作方法；
11. 风险评估；
12. 优化建议和优先级；
13. 投流素材方向；
14. 最终推进结论。

关键判断尽量绑定集数、事件、动作或短台词证据。材料未明确时必须标注，不得把建议新增内容写成参考剧已有事实。

### 11.9 改编方案

Agent 根据当前参考剧的剧本分析主动提出 2-3 套有针对性的改编方案，例如：

- 保留核心冲突，替换人物身份和世界观；
- 保留人物关系，重构事件链和爽点顺序；
- 只提取结构和节奏，重新生成故事与角色。

用户可以：

- 选择一套；
- 组合多套；
- 自己描述新方案；
- 要求 AI 继续修改。

最终方法写入 `adaptation_brief`，并作为后续生成的强制依据。

第一版不建设自动查重或版权风险检测服务。产品只提供来源标记、禁止照搬 Rules、改编差异要求和用户确认；不能向用户承诺已经自动完成版权合规审查。

### 11.10 adaptation_brief

`adaptation_brief` 是整部新剧共用的一份正式产物，不按集拆分。

第一版至少包含：

- 改编目标；
- 选定的改编方法；
- 保留的核心内容；
- 需要替换的内容；
- 新增元素；
- 人物和关系调整；
- 题材、风格和世界观方向；
- 目标集数；
- 单集时长；
- 禁止照搬的内容；
- 必须遵守的用户要求。

`adaptation_brief` 必须同时支持：

- 用户直接编辑字段；
- 用户通过对话要求 AI 修改；
- 查看修改后的完整版本；
- 显式确认后再继续；
- 修改后使旧确认失效并重新确认。

### 11.11 可停止的阶段

视频参考创作是一个完整 Skill，但用户不必被强制运行到最后。第一版应允许用户在以下阶段停止并保留产物：

- 只完成视频转高还原剧本；
- 完成参考剧本和整剧分析；
- 完成 `adaptation_brief`，暂不生成新剧本；
- 完成全部新剧本生成。

用户之后可以从已确认阶段继续，不需要重新上传或重做成功步骤。

### 11.12 后续补传视频

用户在整剧分析或 `adaptation_brief` 已生成后补传当前参考剧的新视频时：

- 新视频仍可加入当前作品；
- 已确认的单集参考剧本不应被无关重做；
- `reference_scripts`、`script_analysis`、`adaptation_brief` 及其下游会受到影响；
- 系统必须提示用户保留现有下游，或从最早受影响步骤重新生成；
- 不能静默把新增集混入旧分析后继续创作。

### 11.13 主要产物

- `video_source`
- `video_script_unit`
- `reference_scripts`
- `script_analysis`
- `adaptation_brief`
- `story_seed`
- `series_blueprint`
- `episode_cards`
- `script_unit`
- `scripts`

`script_analysis` 是视频参考创作 Skill 内部的主要业务步骤和产物，不单独包装成第四个用户 Skill。

## 12. 图片输入

图片属于 Agent Shell 的通用输入，不作为第一版独立 Skill。

Agent 根据用户意图：

- 理解图片并回答；
- 把图片作为人物、场景、风格或其他创作参考；
- 在意图不明确时询问用户希望如何使用。

图片本身不会自动启动剧本生成流程。

独立音频文件不作为第一版输入类型。视频文件中的音频仍由视频解析步骤综合处理。

## 13. 最终剧本与导出

最终剧本以各集 `script_unit` 为编辑真源，`scripts` 只是完整阅读和导出的聚合视图。

第一版至少需要：

- 按集查看；
- 按集编辑和保存；
- 查看当前版本和状态；
- 全集生成完成后导出完整剧本；
- 导出前检查所有目标集数是否存在；
- 有未保存修改或仍在生成时禁止导出错误版本。

第一版必须支持：

- TXT 完整剧本导出；
- DOCX 完整剧本导出。

PDF 不作为第一版必须格式。

## 14. 错误与恢复

第一版至少定义以下用户可理解的错误：

| 场景 | 第一版行为 |
|---|---|
| 文件格式不支持 | 上传前或上传后立即说明，不创建 Run |
| 文件读取/解析失败 | 保留失败状态，允许删除或重新上传 |
| 来源类型不明确 | Agent 追问小说、非小说或其他用途 |
| 缺少集数/时长 | 不启动生成，要求补齐配置 |
| 模型超时或限流 | 标记当前任务失败，保留 cursor，允许重试 |
| 模型输出无法解析 | 不保存为成功产物，进行有限修复或标记失败 |
| 批量部分失败 | 保留成功子项，只重试失败子项 |
| 刷新或网络断开 | 从后端快照恢复，不重复任务和消息 |
| 服务重启 | 恢复作品、Run、产物、版本和待处理审批 |
| 旧版本并发保存 | 拒绝静默覆盖，返回最新版本供用户处理 |
| 下游版本不一致 | 提示保留或重新生成，不静默继续 |

错误提示必须说明：

- 哪一步失败；
- 已完成内容是否保留；
- 用户现在可以重试、暂停、修改输入还是重新上传；
- 是否会产生额外模型调用。

## 15. 数据、隐私与保留

第一版必须明确：

- 作品、对话、文件和产物保存在哪里；
- 哪些原始材料会发送给模型 Provider；
- 用户删除作品或文件时删除哪些数据；
- 视频原文件保存多久；
- 提取后的剧本、分析和改编产物保存多久；
- API Key 和模型凭据不能出现在前端、日志、导出包或版本库；
- 未经允许不能把公司材料发送到未批准的第三方模型服务。

第一版部署为公司内部网页产品。

第一版不建设登录和用户账户体系，采用内部共享工作区。进入系统的内部用户可以看到和操作全部作品，不提供个人作品隔离、角色权限或操作授权。内网访问控制由部署环境承担；产品界面必须明确这是共享空间，避免用户误以为作品仅本人可见。

视频原文件自上传之日起保存 7 天，期限届满后自动删除。视频生成的高还原剧本、整剧分析、`adaptation_brief`、来源文件元数据和版本关系随作品保留。原视频删除后，界面必须提示用户无法再基于原视频重新解析；已有派生产物仍可查看、编辑和继续使用。

模型请求由服务端通过公司内网透传服务发出，浏览器不直接访问模型 Provider，也不持有模型 API Key。内网透传的认证、审计和目标 Provider 配置在阶段 2 定义。

## 16. 第一版明确不做

- 多部参考剧自动融合和权重配置；
- 自动猜测用户是否已经传完全部视频；
- 为每个 Skill 重复建设上传、聊天、审批和编辑器；
- 每个视频子项都要求用户单独点击确认；
- 开放式自主 ReAct 替代业务 Runtime；
- 多人协作、复杂权限和企业组织管理；
- 视频生成、分镜生产和视频片段生产；
- 独立音频文件分析；
- 自动查重和自动版权合规判定；
- 把所有可能的内容生产能力一次性实现；
- 把完整作品内容每轮全部发送给模型。

## 17. 第一版暂定技术约束

以下约束来自当前可行性讨论，用于第一版设计估算，不作为永久产品规则：

- 视频格式：MP4、MOV；
- 单视频时长：不超过 3 分钟；
- 单视频大小：不超过 50 MB；
- 单批视频数量：不超过 20；
- 单作品视频数量：不超过 100；
- 视频解析并发数：3。

这些限制必须配置化。接入豆包正式接口后，根据官方限制、压缩质量和负载测试重新确认。

用户原始视频与发送给模型的处理副本应分开。压缩、转码或抽取不得静默覆盖用户上传的源文件；第一版也不把“统一压缩到 10 MB”写成固定产品规则，实际处理规格由正式模型接口和质量测试决定。

## 18. 第一版成功标准

### 18.1 Agent Shell

- 用户能创建、打开和切换作品；
- 两部作品的数据和上下文不会串用；
- 用户可以显式选择 Skill，也可以由 Agent 正确识别；
- 意图不明确时 Agent 会询问，不擅自启动错误流程；
- 通用输入、任务状态、审批、编辑和错误提示没有明显交互问题。

### 18.2 三个 Skills

- 小说转剧本完整运行并得到目标集数剧本；
- 非小说文本转剧本完整运行并得到目标集数剧本；
- 视频参考创作从分批上传运行到新剧本生成；
- 三个 Skills 的主要步骤都能正确暂停并等待确认；
- 用户修改后能够重新确认并继续；
- 失败步骤可以从正确位置重试。

### 18.3 产物

- 所有用户可见主要产物可以阅读和编辑；
- 手动编辑与 AI 修改都会生成新版本；
- 用户可以重新生成当前步骤或单集剧本；
- 下游使用的上游版本可追踪；
- 最终剧本可按集查看和继续修改。

### 18.4 上下文

- 主 Agent 能识别当前作品、当前 Skill 和当前步骤；
- Worker 不需要读取无关的完整作品内容；
- 选区修改能准确定位；
- 跨步骤引用读取已确认的正确版本；
- 项目之间默认上下文隔离。

### 18.5 可执行验收场景

阶段 2 的验收设计至少覆盖：

1. 创建两部作品，分别上传材料、对话和运行 Skill，刷新与切换后数据不串用；
2. 从两个内部浏览器会话进入共享工作区，均能看到同一作品列表；并发编辑旧版本时不能静默覆盖；
3. 直接选择 Skill、自然语言自动路由、意图模糊追问三种入口均正确；
4. 只上传文件、查看文件和闲聊不会创建 Run；
5. 同一作品存在活动 Run 时输入框禁用，冲突操作不会启动第二个写入任务；
6. 不同作品可以同时运行，状态和产物不会交叉；
7. 小说和非小说链分别完成一次超过 5 集的真实批处理；
8. 视频分两批以上上传，用户明确“传完了”后再进入整剧分析；
9. 视频批次包含缺集、重名、无集号和单集失败，状态与恢复操作正确；
10. 视频 Skill 分别在“剧本已确认”“分析已确认”“Brief 已确认”处停止并恢复；
11. 每个主要步骤都验证编辑、AI 修改、重新生成、确认和版本递增；
12. 修改上游后分别验证保留下游和重生成受影响下游；
13. 模型超时、结构错误、网络断开和服务重启后能够恢复；
14. 最终目标集数完整，单集可编辑，TXT/DOCX 导出与聚合阅读内容一致；
15. 从历史候选改选最终稿时需要确认，旧最终稿和其他候选仍可追踪。

内容质量验收不能只看 JSON 成功或流程完成。第一版使用下述固定材料做基础内容评审，流程稳定后再扩展样本量和题材覆盖。

### 18.6 第一版测试材料

第一版采用以下测试集：

| Skill | 测试材料 | 使用方式 |
|---|---|---|
| 小说转剧本 | 由产品负责人提供 1 本真实小说 | 反复回归，覆盖配置、拆集、分集卡、剧本、修改、确认和重生成 |
| 非小说文本转剧本 | 由开发 Agent 从 0 到 1 编写一套非小说测试材料 | 同一故事准备完整大纲、简略梗概和零散设定等不同完整度输入 |
| 视频参考创作 | 由产品负责人后续提供 1 部几十集的完整剧集 | 验证分批上传、排序、解析、整剧分析、Brief 和新剧本生成 |

测试材料少而固定，适合第一版反复定位流程回归。它不能证明模型对所有题材的泛化质量；扩大题材和样本量属于流程稳定后的质量阶段。

### 18.7 第一版验收优先级

第一版优先保证：

1. 三条主链能够完整跑通；
2. 中间步骤、审批、编辑、版本、暂停、恢复和重试正确；
3. 项目、上下文、输入输出和候选版本不会串用；
4. 视频批量任务能够处理几十集完整剧集；
5. 最终得到可编辑、可确认、可导出的分集剧本。

内容质量在流程门禁通过后进行基础评审，不以一次模型结果的主观优劣阻塞底层流程验证。

### 18.8 Agent 内容评审边界

开发 Agent 可以承担第一轮内容评审，包括：

- 结构字段是否完整；
- 上下游事实是否一致；
- 集数、人物、关系和事件是否自相矛盾；
- 剧本是否符合格式；
- 视频分析判断是否有证据引用；
- 改编结果是否遵守已确认 `adaptation_brief`；
- 是否出现明显遗漏、重复、无依据新增或上下文串用。

但同一个 Agent 既参与生成又参与评审时，不构成独立质量证明。第一版允许以 Agent 评审为主、产品负责人抽查关键结果；正式上线前如需更高可信度，再增加独立模型评审或业务编剧评审。

视频高还原评审优先级：

```text
剧情与人物关系
→ 反转和尾钩
→ 主要对白
→ 全部逐句对白
→ 精确时间码
```

剧本分析中，剧情、人物、分集事件和引用证据属于事实层，必须准确；爆款评分、风险判断和优化建议属于判断层，要求合理、有依据，不要求存在唯一答案。

### 18.9 时长与成本

- 第一版不设置独立的产品耗时 SLA，单次模型请求先按公司内网透传网关允许的最大时长配置；
- 超过网关上限按超时失败处理，并保留可重试 cursor；
- 整剧任务展示实际步骤和批量进度，不向用户承诺尚未验证的完成时间；
- 第一版不把单部作品模型成本作为验收门禁；
- 流程稳定后再基于真实调用记录评估并发、时长和成本优化。
