## 2. 一句话结论

项目最终建立了正确的产品与工程底座，但前半程的推进顺序不够严格：原型、视觉、正式实现、模型接入和状态机设计互相穿插，很多机制先以局部补丁出现，再被迫重构为通用能力。真正高效的转折点出现在 7 月 13 日的全量审计之后：从“用户指出一个问题就修一个问题”改为“按数据真源、状态权威、上下文编译、修改粒度和验收矩阵成组治理”。

本项目最重要的经验不是“以后多写测试”，而是：**先建立唯一产品合同和状态权威，再做界面与模型；先定义测试矩阵，再实现；每一阶段必须凭可执行证据退出，不能凭截图、一次成功或主观感觉宣布完成。**

## 3. 原定流程与实际节奏

项目采用的通用 12 步流程是：

1. 需求澄清
2. PRD / 用户故事
3. 信息架构 / 原型
4. UI / UE 规范
5. 技术方案
6. 前端实现
7. 后端 / API / 数据库
8. 测试计划
9. E2E 验证
10. 部署上线准备
11. 监控维护与用户验收
12. 复盘迭代

实际过程不是 1 到 12 的直线，而是四个波段：

| 波段 | 时间 | 实际工作 | 节奏判断 |
|---|---|---|---|
| 产品与架构探索 | 6 月 24 日前后 | 两条链、Prompt/Skill、Main Agent、Go/TS、Eino 方向 | 方向基本正确，但合同没有完全冻结 |
| 原型与视觉反复 | 6 月 24 日至 6 月 30 日 | Mock、状态页、Figma、三栏工作台、编辑器选型 | UI 先于状态语义稳定，返工最多 |
| 正式实现与真实模型纠偏 | 7 月 1 日至 7 月 11 日 | React、Go、Claude、Gemini、运行态、局部修改、双链 live | 一次次真实路径暴露合同与实现不一致 |
| 系统治理与发布收口 | 7 月 13 日至 7 月 20 日 | 54 项审计、52 项整改、Eino、长篇分批、上下文压缩、发布门禁、文档合并 | 节奏转为系统性治理，质量提升最快 |

最大节奏问题是第 3 至第 8 步没有形成严格准入关系：原型被当成实现、视觉稿被当成状态合同、API 合同被当成可运行后端、一次 live 成功被当成完整 E2E。后续项目应允许并行探索，但不能允许“阶段结论混用”。

## 4. 分阶段复盘

### 4.1 需求澄清与产品边界

做对的事情：

- 明确旧项目与新项目隔离，避免污染旧主流程和旧输出；
- 明确小说与非小说是两条不同前置链，最终汇合到剧本生成；
- 明确主控模型负责意图与流程，内容模型负责产物；
- 明确用户需要作品级独立工作区，而不是临时单次生成页；
- 明确主要产物必须逐节点确认，内部 `script_context` 不应暴露。

踩坑：

- “聊天、生成、查看、修改、重生成”五类行为最初没有完整写成用户故事；
- 作品入口与持久化不是第一天就确定，后来出现刷新后像“项目丢失”；
- 上传附件一度被默认等同于小说和生成意图，而实际附件可以是任意材料；
- 生成配置、保留原分集、是否需要集数等规则在实现中才逐步厘清。

根因：产品目标明确，但边界条件和反例不完整。团队知道“主流程是什么”，却没有同等清楚地定义“什么情况下绝不能启动主流程”。

后续最优做法：先交付一张用户意图表，至少覆盖闲聊、提问、上传、查看、明确生成、模糊修改、明确修改、失败追问、重试、暂停、继续、手动编辑和切换作品。每一项都写明是否启动 Run、需要什么上下文、是否追问、是否影响下游、前端显示什么。

退出门槛：20 至 30 条代表性话术由产品、Agent、前端、后端共同判定，不能存在四方解释不同的情况。

### 4.2 PRD、用户故事与状态合同

做对的事情：后期补齐了 Run、Task、Approval、Artifact、Version、Stale、Invalidated、Failed Cursor 等正式概念，并最终由 Go Runtime 统一掌握业务状态。

踩坑：

- 早期“已生成、待确认、已确认”在 UI 与后端中的含义不同；
- 模型一边询问用户是否修改，一边已经开始执行；
- 上游修改时曾直接清掉所有下游，而不是先保存新版本再询问；
- Approval 失败时前端曾移除确认卡，使用户失去恢复入口；
- 暂停最初只是视觉状态，不能真正取消正在运行的模型请求；
- 失败重跑曾允许重跑未失败步骤，且没有从失败 task cursor 续跑。

根因：状态名先出现，状态迁移规则后补；没有先定义“不变量”。

后续最优做法：在代码前先画出唯一状态机，并把以下不变量写成自动测试：

- 追问阶段不得执行内容修改；
- 用户确认前不得失效或删除下游；
- 没有实际下游时不出现下游处理确认；
- 失败只能从失败任务恢复；
- 运行中禁止并发人工编辑和新的执行请求；
- 每个动作只能有一个最终状态和一条用户回复。

退出门槛：状态迁移表可直接生成测试用例，API、前端和 Agent 不再自行解释状态。

### 4.3 信息架构与原型

做对的事情：形成作品入口、左侧目录、中间产物/剧本、右侧 Agent 的工作台模型，并区分输入材料、过程产物和最终剧本。

踩坑：

- 最初左侧目录甚至被做成输入区；
- 输入材料、过程产物、剧本的宽度和滚动容器不一致，切换时页面跳动；
- 过程产物没有内容时仍显示空入口；
- 长产物滚动时目录跟着消失；
- 编辑态把目录挤到顶部横向区域，用户失去定位能力；
- 三栏收起后恢复按钮集中在右上角，用户不知道它控制哪个面板；
- 单纯隐藏 Grid 子项后，剩余内容自动补列，甚至进入 0px 列。

根因：只画静态默认状态，没有先列全布局组合和滚动所有权。

后续最优做法：原型阶段必须先完成“页面区域 × 数据状态 × 面板开合 × 视口”的矩阵。三栏至少验证全开、仅左关、仅右关、两侧都关、逐项恢复；内容区至少验证空、短、长、编辑、待确认、运行、失败。目录固定，只有正文滚动；面板恢复入口贴近被隐藏的边缘。

退出门槛：所有布局组合都能在可点击原型中走通，且每个按钮的作用对象在视觉位置上可推断。

### 4.4 UI / UE 规范与视觉实现

做对的事情：最终形成统一三栏、Lexical 剧本编辑器、响应式分区、过程产物阅读/编辑、分集目录、运行摘要和简化过程记录。

踩坑：

- 前期花了多轮 Figma 和视觉调整，但状态语义仍在变化；
- 组件库没有先稳定，就开始复制状态页，导致按钮、图标、边框、间距反复修；
- 一度出现空白 Frame、文字溢出、图标占位方块、按钮内容不居中；
- 用户每指出一处才修一处，没有主动做全局视觉扫描；
- 过程记录展示全部底层步骤，信息噪声过大；
- 编辑器保留了无效“动作”下拉框，U/S 格式按钮未真正生效；
- 分集目录发生文字与状态重叠、高度不齐。

根因：视觉验收围绕“某张截图好不好看”，没有围绕组件、状态和几何规则自动化。

后续最优做法：顺序必须是设计令牌 → 基础组件 → 复杂组件 → 状态页 → 真实数据页。视觉检查不只看默认截图，还要做固定视口、长文本、最长中文字段、全部开合组合、加载/空/错/禁用态和键盘焦点检查。静态稿不能拥有独立于产品合同的行为。

退出门槛：组件源页先通过，再批量进入状态页；每个状态有截图、溢出检查和可访问性检查。

### 4.5 技术方案与架构

做对的事情：最终确定 TypeScript/React 前端、Go 后端、Claude 主控、Gemini 内容模型、Eino 编排、SQLite 持久化；Eino 不接管业务状态，Go Runtime 仍是唯一权威。

踩坑：

- 最早 Python 原型、Go Mock Runtime、正式 Go Runtime 并存，命名长期保留 `mock`；
- 一度存在新旧两套执行路径；
- Main Agent、代码 Guard、前端 Source Mode 都能改写意图，形成多套权威；
- Prompt 和 Skill 虽在仓库中，早期模型调用并未真正拼装消费；
- “输出 schema 看起来一样”曾被误认为 Prompt/Skill 已接通；
- Eino 接入较晚，前面有些运行机制先写成了临时编排。

根因：技术选型已经确定，但职责边界和迁移终态没有一开始写成不可变架构原则。

后续最优做法：先定义五个唯一权威：意图权威、流程状态权威、内容真源、版本权威、配置权威。框架只负责编排，业务状态不放进框架私有内存。任何兼容路径必须有删除日期和契约测试。

退出门槛：用一张责任矩阵回答“谁能决定、谁能执行、谁能保存、谁能显示、谁能恢复”，每一行只能有一个最终负责人。

### 4.6 前端正式实现

做对的事情：从原型转成 React，建立作品中心、SSE 恢复、Artifact 工作区、Lexical 编辑器、选区引用、脏数据保护、错误边界和响应式模式。

踩坑：

- 早期把 Mock/Spike 当作接近完成的前端，但实际编辑器不可用；
- `contentEditable` 与正式 Lexical 合同不一致；
- Agent 更新后的 Artifact 被旧前端编辑缓存遮住，甚至可能反向覆盖；
- 发送框、运行中禁用、刷新后的选中项、引用清理等细节反复遗漏；
- 选区最初用文本 `indexOf` 反查，重复台词和跨行选择会定位错误；
- 前端二次刷新失败曾被静默吞掉，用户以为保存成功且状态已同步。

根因：组件实现先围绕可见界面，数据版本、并发和恢复行为后补。

后续最优做法：前端从第一天就使用真实 API 类型和稳定 ID；编辑缓存键包含 Artifact ID 与版本；保存必须提交 `base_version`；选区由编辑器节点 ID 产生，不能从纯文本倒推；所有异步动作明确 idle/loading/success/error/conflict/recovering 六类状态。

退出门槛：刷新、双标签页、后台 Agent 更新、未保存离开、409 冲突、跨行选区都通过组件/API 集成测试。

### 4.7 后端、API、数据库与运行时

做对的事情：最终将作品、聊天、附件、Run、Event、Artifact、Approval 持久化到 SQLite；统一正式路由、结构化错误、SSE、版本锁、暂停恢复、失败 cursor 和发布数据迁移。

踩坑：

- 最初作品、聊天和附件只在内存，服务重启后消失；
- 项目 ID 计数重启后可能撞号；
- Run 运行中重启会永久卡在 running；
- Artifact 保存缺少版本锁，旧页面可以覆盖新版本；
- 持久化错误曾被静默吞掉，业务失败大量伪装成 HTTP 200；
- SQLite busy 暴露并发写入与重试不足；
- 已失效 Artifact 与 Run 的 `invalidated_artifacts` 一度不同步；
- 后端已有 SSE，但前端早期仍轮询，能力没有闭环。

根因：先做了“能跑”的接口，后补数据生命周期和失败语义。

后续最优做法：数据库模型和事务边界先于 Handler；所有写操作定义幂等键、版本条件、错误码和恢复动作；服务启动必须执行 orphan running reconciliation；健康检查不仅看进程，还看存储可写、schema 版本和队列状态。

退出门槛：重启、并发保存、数据库忙、未知项目、超大请求、SSE 断线、旧 schema、持久化失败均有 API 测试。

### 4.8 Agent、Prompt、Skill 与模型链

做对的事情：最终形成“主控只判断，内容模型执行”的职责；Prompt 是任务合同，Skill 是规则库；两条链使用各自前置步骤并共享剧本生成。

踩坑：

- 主控早期依赖关键词枚举，语义泛化弱；
- 代码 Guard 为纠错而不断增长，后来反过来覆盖模型的正确判断；
- Claude 原始回复、Guard 后决策和前端显示文案曾不一致；
- 主控会回复“稍等，我来看看”，但系统没有对应异步动作；
- 模糊追问如“这句话”“改啊”“继续”缺少稳定 pending context；
- 附件曾被自动当小说读取，没有遵循用户意图；
- 用户只是咨询修改建议时，也可能被强制执行修改。

根因：没有从一开始区分 `model_decision`、`guarded_decision`、`executed_action` 和 `user_reply`，也没有定义追问上下文生命周期。

后续最优做法：Main Agent 输出结构化决策，代码 Guard 只处理安全与确定性约束，不能重做语义分类；执行后由真实动作结果生成一次用户回复。保存决策追踪，能回答“模型怎么判、Guard 是否改写、最终执行什么”。Pending intent 必须有目标、缺失槽位、有效期和消费规则。

退出门槛：基于真实对话样本建立意图回归集，覆盖肯定、否定、反问、省略、连续追问、跨轮指代和执行失败后的对话。

### 4.9 上下文、定位、局部修改与下游刷新

这是项目中返工最深、也最有复用价值的一环。

做对的事情：最终形成字段、实体、集合、区块、剧本选区、场景、单集和整体重生成的通用粒度；内容模型返回 sparse patch；版本递增；有实际下游时让用户选择保留或重生成。

踩坑：

- 早期局部修改虽然只替换目标字段，却把完整原文、完整 Artifact 和大量历史都传给模型；
- 简单改一句话也可能发送整集甚至全文，导致超时、成本增加和模型误改；
- 某个 Artifact 的局部修改修好后，没有立即验证所有 Artifact 的所有粒度；
- 集合操作最初缺失，无法正确拆集、合集、插入或移动条目；
- 上游修改曾直接删除全部下游，而正确行为应是先保留并询问；
- 剧本选区引用发送后没有进入聊天消息，或发送后引用没有从输入区清除；
- 用户在模型 Run 中编辑上游，会让已在运行的下游使用旧快照，造成污染。

根因：把“局部修改”理解为输出局部，而没有同时约束输入局部、定位稳定、合并确定、并发安全和下游影响。

后续最优做法：把一次修改拆成七步固定管线：

1. 识别意图；
2. 定位稳定目标 ID；
3. 选择修改粒度；
4. 按预算编译最小上下文；
5. 校验 sparse 输出；
6. 在版本锁内确定性合并；
7. 计算实际下游影响并等待用户选择。

上下文必须按任务编译，而不是统一“尽量多给”：主控拿摘要、当前目标和近轮对话；内容模型拿目标片段、相邻窗口、必要依赖和稳定 ID。运行中禁用会改变依赖的人工编辑。

退出门槛：为两条链的每个主要 Artifact 建立“字段/实体/集合/区块/整体”矩阵，剧本建立“单行/跨行/场景/单集”矩阵；每格同时验证输入、输出、合并、版本、前端刷新和下游处理。

### 4.10 长篇处理、批次与性能

做对的事情：小说拆集改为全局骨架、每批最多 5 集的边界定界、确定性合并和检查点；分集卡也按 5 集批次执行；模型超时向用户明确显示“模型服务超时”。

踩坑：

- 早期每次模型调用携带全部有效 Artifact 和完整原文，单次上下文曾达到约 11 万字符；
- 约 9900 字输入也遇到 120 秒 504，前端看起来像断线；
- “800 字边界窗口”一度被当固定策略，而实际应按平均体量自适应；
- 对 30 集一次性输出的策略理解不一致；
- 故事圣经是否分阶段曾被讨论，但用户明确不希望为了规避慢模型而改变产品产物语义。

根因：模型调用设计围绕逻辑步骤，而不是围绕时延预算、上下文预算、输出预算和可恢复批次。

后续最优做法：每个模型节点在设计时就声明输入字符/token 上限、最大输出、超时、批次大小、检查点和合并校验。批次是内部执行方式，不改变用户可见 Artifact。长文先做全局骨架保证分配，再做局部窗口，最后由代码校验覆盖、顺序、缺口和重叠。

退出门槛：短、中、长三个规模的基准测试；记录 P50/P95 耗时、输入输出量、重试率、失败恢复位置和单作品成本。

### 4.11 测试、E2E 与用户实测

做对的事情：后期建立 Go、Vitest、编辑器 Gate、API、真实双链、浏览器多视口和发布门禁；用户持续用真实作品验证，发现了自动化没有覆盖的高价值问题。

踩坑：

- 多次过早说“已经完整回归”，但实际只覆盖默认状态或一个 Artifact；
- 测试偏机制存在和 Happy Path，没有验证所有数据形态与组合；
- 面板开合只测默认页面，用户连续点击后才暴露 Grid 错列；
- 非小说链有时没有随小说链同步回归；
- 真实模型成功一次，被误认为上下文、意图和修改都完全正确；
- “开启监控”后助手多次结束回复，没有持续观察到用户明确叫停，属于协作执行失败。

根因：没有明确测试声明的范围，使用了“全部、完全、都正确”等超过证据的结论；测试矩阵没有把链路、节点、粒度、状态、视口和故障做笛卡尔覆盖取舍。

后续最优做法：每次回归报告必须列出“已测、未测、模拟、真实模型”四类；禁止无证据使用“全量”。建立三层测试：确定性单元/契约测试，高风险浏览器 E2E，少量真实模型 Golden Flow。监控任务使用长驻命令持续读取增量日志，只有用户说停止、进程退出且无法恢复、或需要授权时才结束。

退出门槛：发布候选必须有一份可复现的测试清单、Run ID、模型与运行时元数据、失败注入结果和未覆盖风险。

### 4.12 部署、发布、文档与交接

做对的事情：完成统一正式包、启动/停止、备份/恢复、日志查看、数据库版本保护、Release Gate；最终把大量历史合同归档，只保留七份现行核心规范和运行时 Prompt/Skill。

踩坑：

- 仓库很长时间没有有效提交，无法用 Git 历史重建过程；
- README、Mock 命名、Python 原型、编辑器 Spike 和旧合同长期共存；
- `preview.html` 累积大量互相矛盾的历史文档，用户无法判断哪个最新；
- 第一个超长对话持续太久，响应变慢、上下文压缩和遗漏风险上升，交接发生得太晚；
- 多个接续对话依赖自然语言摘要，没有统一机器可读的当前状态快照。

根因：把文档当累计记录，而不是分成“现行真源、决策记录、历史归档”；把聊天上下文当项目记忆，而没有仓库内持续维护的交接文件。

后续最优做法：从第一天初始化 Git；每个阶段结束形成小提交和决策记录；文档分为 Current、ADR、Archive 三层。每当线程超过约 150 至 200 个实质回合、阶段切换或上下文明显变慢时，生成仓库内 `CURRENT_HANDOFF.md`，包含当前阶段、已完成、未完成、已知风险、服务状态、测试证据和下一条命令。

退出门槛：新对话只读 5 分钟文档就能准确继续，不需要依赖旧助手“记得大概”。

## 5. 反复返工的七个共性根因

1. **阶段结论越界**：Mock、合同、截图和一次 Live 各自只能证明一件事，却常被表述为整个阶段完成。
2. **多套权威并存**：模型、Guard、前端、Runtime 都曾对意图、配置或状态拥有部分决定权。
3. **先做实例，后做通用模型**：先修某一句、某一集、某个 Artifact，之后才抽象出全流程修改矩阵。
4. **测试跟着 Bug 走**：用户指出问题后才补对应测试，初期没有从不变量和组合空间生成测试。
5. **输入范围缺少预算**：只关注模型输出是否局部，没有控制模型输入是否最小必要。
6. **视觉与业务状态脱节**：静态稿和真实运行态分别演进，导致“看起来对、行为不对”。
7. **项目记忆依赖对话**：长线程和多次接续增加了上下文压缩、重复检查和遗漏的成本。

## 6. 哪些做法最有效

- 用户坚持用真实操作路径而不是只看代码，发现了大量状态与认知问题；
- 把 54 项问题一次性按 P0/P1/P2/P3 分类，结束了零散修补节奏；
- 作品级工作区和 SQLite 持久化解决了“内容丢失”的根本问题；
- Go Runtime 保持业务状态唯一权威，Eino 只做编排，避免双状态机；
- 主控模型与内容模型分工，减少控制逻辑和内容生成相互污染；
- Sparse Patch、稳定 ID、`base_version` 和下游确认组成了完整修改闭环；
- 长篇步骤采用内部批次和检查点，同时保持用户只看到完整正式产物；
- 最后将 Preview 收敛为七份现行规范，历史文档归档，重新建立了文档真源。

## 7. 后续同类项目的最优 12 步执行法

### 第 1 步：需求澄清

产出：目标用户、核心任务、非目标、两条以上真实用户路径、禁止行为。  
门槛：任何人能回答“何时不执行”。

### 第 2 步：PRD / 用户故事

产出：意图表、状态表、异常流、作品/项目模型、审批与修改故事。  
门槛：正常、边界、失败路径都有验收语句。

### 第 3 步：信息架构 / 原型

产出：页面区域、导航、滚动所有权、空/长/错/运行/编辑态和面板组合。  
门槛：可点击原型走通所有主路径，不包含假业务承诺。

### 第 4 步：UI / UE 规范

产出：令牌、组件、状态、响应式、编辑器和可访问性规范。  
门槛：组件源页和关键状态截图通过，再允许复制页面。

### 第 5 步：技术方案

产出：唯一权威矩阵、状态机、数据模型、版本策略、上下文预算、模型职责。  
门槛：每个状态和数据只有一个写入权威。

### 第 6 步：前端实现

产出：真实 API 类型、组件状态机、错误/冲突/恢复、编辑器稳定定位。  
门槛：不依赖 Mock 特例即可连接契约测试服务器。

### 第 7 步：后端 / API / 数据库

产出：事务、正式路由、结构化错误、幂等、版本锁、事件、重启恢复。  
门槛：故障注入和重启测试通过，不只 Happy Path。

### 第 8 步：测试计划

这一步的设计应在第 2 步开始，正式实现随第 6、7 步同步。  
产出：不变量测试、契约测试、交互矩阵、真实模型 Golden Flow、性能预算。  
门槛：每个需求都能映射到自动或人工测试证据。

### 第 9 步：E2E 验证

产出：双链路、全部主要节点、修改粒度、下游处理、刷新/重启、故障恢复证据。  
门槛：明确列出已测与未测；没有 P0/P1；用户路径回归通过。

### 第 10 步：部署上线准备

产出：正式包、配置隔离、备份恢复、日志、安全停止、升级迁移和 Release Gate。  
门槛：干净环境可安装、启动、使用、备份、恢复和卸载。

### 第 11 步：监控维护与用户验收

产出：真实任务记录、P50/P95 时延、模型成本、失败分类、发布候选问题清单。  
门槛：连续一段观察期无阻断问题，已知风险有明确处置。

### 第 12 步：复盘迭代

产出：本类文档、ADR、测试缺口、下一版本范围。  
门槛：把教训转成流程、代码门禁或模板，而不是只留一句经验。

## 8. 推荐的开发节奏

每个功能采用同一个小循环，通常控制在半天至两天：

1. 先写一个用户故事和反例；
2. 补状态/API/数据合同；
3. 先写关键不变量测试；
4. 实现最小纵向闭环；
5. 跑确定性测试；
6. 跑浏览器真实交互；
7. 必要时跑一次真实模型；
8. 更新现行文档和交接状态；
9. 小提交收口。

不要连续数天只做视觉，也不要连续数天只堆后端。最有效的单位是“一个用户可验证的纵向能力”，例如“选中跨行剧本 → 对话中携带引用 → 主控定位 → 内容模型局部修改 → 新版本刷新 → 下游确认”。

## 9. 推荐的质量与效率指标

产品正确性：

- 意图回归集准确率及错误类型；
- 错误执行率，尤其是“用户只问不改却执行”；
- 修改越界率和下游误失效率；
- 刷新/重启恢复成功率。

模型效率：

- 每种操作的输入/输出字符或 Token P50/P95；
- 本地修改相对整份 Artifact 的上下文比例；
- 超时率、重试率和批次恢复率；
- 每集、每作品成本。

工程质量：

- 状态机、Runtime、Worker、API、前端关键模块覆盖；
- Release Gate 时长与稳定性；
- 409、SQLite busy、断网、504 等故障注入通过率；
- 大文件和条件分支增长趋势。

协作效率：

- 每轮返工是否来自未定义合同；
- “宣称完成后被用户立即推翻”的次数；
- 对话长度和交接次数；
- 每个问题从发现到形成通用回归测试的时间。

## 10. 多对话接续开发规范

每次接续必须先读取仓库内的当前交接，不允许只依赖聊天摘要。交接至少包含：

- 项目绝对路径和禁止修改范围；
- 当前 12 步阶段；
- 当前服务地址和存活状态；
- 已完成能力及其测试证据；
- 正在进行的唯一任务；
- 未解决问题及优先级；
- 数据库、Run、测试作品等诊断定位；
- 最近一次完整测试结果；
- 下一条建议命令。

新对话开始时先验证会变化的事实，例如服务、测试、Git 状态；对稳定的产品决定直接继承。长时间监控任务必须保持工具会话运行并按增量日志分析，不能发送一次状态后自行结束。

## 11. 当前项目判断

截至 2026-07-20，项目已经完成第 10 步发布准备，进入第 11 步用户验收与发布候选观察。当前架构方向已经收敛：

- React/TypeScript 前端；
- Go Runtime 与 API；
- SQLite 作品和运行态持久化；
- Claude 主控、Gemini 内容模型；
- Eino 负责节点编排，Go Runtime 负责业务状态；
- 两条生成链、版本化 Artifact、通用局部修改和下游确认；
- 长篇拆集与分集卡批处理、检查点和失败续跑；
- 正式包、备份恢复、日志、安全停止和 Release Gate。

当前不应再扩大主流程功能。第 11 步应重点观察：

1. 真实长任务的模型超时、成本和批次稳定性；
2. 小说与非小说真实内容质量，而不只是结构正确；
3. 连续修改、暂停、失败恢复和重启后的数据一致性；
4. 多个作品长期使用后的 SQLite 并发和体量；
5. 用户是否能准确理解确认、保留下游、重生成和版本状态。

不能声称“从此没有 Bug”。能够成立的结论是：当前已无已知 P0/P1 阻断项，工程门禁完整，剩余工作属于发布候选的真实使用观察和新缺陷收敛。

## 12. 最终方法论

这次开发证明，Agent 产品的难点不是把模型接上，也不是把三栏页面画出来，而是让以下五件事始终一致：

1. 用户认为自己说了什么；
2. 主控判断要做什么；
3. 内容模型实际收到什么；
4. Runtime 实际修改并保存什么；
5. 前端最终展示和恢复什么。

只要其中任意两层存在不同真源，就会出现“回复和执行不一致”“局部修改却重做全文”“前端更新了但后台没保存”“刷新后像丢项目”“确认还没点就开始执行”等问题。

后续项目追求效果和效率最大化的核心，不是减少设计，也不是增加更多文档，而是让每一份合同都可执行、每一个阶段都有退出门槛、每一次修复都进入通用矩阵、每一个完成结论都与证据范围严格一致。
