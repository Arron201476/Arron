Novel2Script Agent 整体框架

当前设计目标：把“主 Agent 自主计划 + prompts 作为内部能力 + 可配置审批点 + artifacts 工作台”定义清楚，再进入 SDK 或工程实现。

当前结论

已具备

小说转剧本主流程

已有 `小说-prompts`：全文理解、拆集、分集规划。这些不是前端按钮，而是 Main Agent 可调用的内部能力；剧本生成需要抽成通用能力。

已补齐

非小说转剧本主流程

已有 `非小说-prompts`：素材库、故事种子、系列蓝图、分集规划。之后与小说链在 `episode_cards` 汇合。

统一汇合点： 两条链路都产出 `episode_cards`，再经 `script_context_adapter` 转成统一 `script_context`，最后调用通用 `script_generate`。

整体 Agent 架构

用户输入大文本 / 文件 / 局部修改 / 聊天指令
→
Main Agent意图识别、路由、状态管理
→
Subagents按流程调用 prompts + skills
→
Artifacts中间产物、上下文、可恢复点
→
前端 Agent 面板展示计划、进度、结果、可打断

Main Agent 职责边界

1. 意图识别

判断用户是小说转剧本、非小说转剧本、修改已有产物、局部改写、项目管理，还是普通问答。

2. 自主计划

根据目标和当前 artifacts 制定执行计划，选择要调用的 capabilities、subagents 和审批点。

3. Artifacts 管理

记录每一步输入、输出、用户确认版本、可恢复 checkpoint，避免后续步骤读错旧产物。

4. 上下文装配

每次调用模型前装配最新 `context_pack`，而不是把所有上下文逻辑塞进 prompt。

5. 打断与继续

支持暂停、取消、用户插话、局部重跑；恢复时从 checkpoint 和 artifact 状态继续。

6. 风险提示

当输入不足、集数不匹配、原文钩子弱、用户修改影响下游时，先提示风险再执行。

审批策略：不是按钮流，是运行模式

Agent 可以连续执行，也可以像当前 Codex 一样在关键动作前请求用户批准。审批点属于运行策略，不属于固定 UI 步骤。

自动执行

Auto Run

Agent 自己制定计划并连续调用 capabilities；只在失败、风险高或需要用户输入时暂停。

关键点审批

Checkpoint Approval

在覆盖已有产物、重排结构、改集数、批量修改、多 artifact 级联影响时请求确认。

每步审批

Step Approval

每生成一个关键 artifact 就暂停，用户确认后再继续，适合高控制场景。

审批卡片应该长这样

[审批请求] Agent 准备执行：build_story_bible 将生成 / 更新：story_bible, characters 可能影响：episode_split, episode_cards, script_context 风险：人物关系一旦确认，后续拆集和剧本会继承 操作：[继续] [修改要求] [暂停] [自动执行后续]

两条主能力链：内部工具，不是按钮流

小说链：原文约束型改编

source_text → capability: build_story_bible → capability: split_episodes → approval/artifact: confirmed episode_split → capability: plan_episode_cards → capability: build_script_context → capability: generate_script

核心约束：原文顺序、原文事实、source_refs、用户确认后的拆集结果优先。

非小说链：故事生成型开发

user_material → capability: build_material_bank → capability: expand_story_seed → capability: design_series_blueprint → capability: plan_episode_cards → capability: build_script_context → capability: generate_script

核心约束：允许原创补全，但必须标记来源；不能把 inferred 内容伪装成用户素材。

通用剧本生成层

小说和非小说输入不同，所以不应该让 `script_generate` 自己判断一堆分支。更稳定的方式是先走 `script_context_adapter`。

script_context_adapter

  • 识别来源：`novel` / `non_novel`
  • 把不同链路产物转成统一 `script_context`
  • 明确事实约束、允许补全、禁止改动、上下文状态
  • 把判断从写作 prompt 中剥离

script_generate

  • 只负责把单集卡写成剧本
  • 只读取统一 `episode_card + script_context`
  • 不负责判断用户输入类型
  • 不负责修改上游规划

Eino Runtime 与前端壳子

当前主方案是 Go 后端内置 Eino Agent Runtime。正确顺序是先定义最小壳子契约，再让 Go mock runtime 按这个契约输出事件和 artifacts；闭环稳定后替换为真实 Eino runtime。

Runtime 侧先做什么

  • Main Agent：意图识别、计划、审批点、工具调用。
  • Capabilities：把 prompts 包成可调用工具。
  • Artifact Store：保存版本、确认态、上下游依赖。
  • Run Events：输出 thinking、tool_call、artifact_update、approval_request。

前端壳子最少要有什么

  • 左侧 artifact 目录。
  • 中间 artifact editor。
  • 右侧 Agent chat 为主，timeline 和审批卡嵌入聊天流。
  • 审批卡片：继续、修改要求、暂停、自动执行。

结论：不需要先做完整前端，但需要一个薄壳子，否则 runtime 生成的审批请求、工具调用过程和 artifact 更新没有稳定展示位置。

下一步落地顺序

  1. 补 `agents/main_agent_router.md`，定义意图识别、计划输出、审批策略和 run events。
  2. 新增 `schemas/artifacts.md`，统一 artifact 字段、版本、确认态和依赖关系。
  3. 新增 `通用-prompts/script_context_adapter.md`，把小说/非小说产物转成统一剧本上下文。
  4. 把当前小说 `step4_script_generate.md` 抽成 `通用-prompts/script_generate.md`。
  5. 搭一个最小前端壳子：左目录、中编辑器、右 Agent timeline/审批卡。
  6. 基于 Go mock agent runtime 接入 Main Agent runner，先跑端到端最小闭环；稳定后替换为 Eino。

技术路线更新：Go + Eino

当前项目已经定为 TypeScript 前端 + Go 后端 + CloudWeGo Eino Agent Runtime。此前提到的 Claude Agent SDK 只作为历史候选方案，不再作为主 Agent 框架。Claude 仍可作为模型 provider 使用，但 Main Agent 的状态机、审批、事件流和 artifact 管理都放在 Go 后端。

为什么改为 Eino

  • 后端主体是 Go，Agent Runtime 放在 Go 内更自然。
  • Eino 支持 agent、workflow、streaming、interrupt/resume 和 callback，和当前设计契约更贴合。
  • 避免额外维护 TypeScript Agent Worker 与 Go 后端之间的状态同步。

下一步

  • 先做 Go mock agent runtime。
  • mock 返回 run events、artifact updates 和 approval requests。
  • 前端和 Go 状态机闭环稳定后，再把 mock runtime 替换为 Eino。
